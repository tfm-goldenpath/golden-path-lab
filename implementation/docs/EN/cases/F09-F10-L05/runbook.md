# Provenance family: F09 / F10 / L05

Read the [operational oracle](record.md) before interpreting results. These are
functional integration checks, not pilot/campaign measurements. Human review is
pending. Tools and trust profiles remain pinned.

From the repository root:

```bash
export PATH="$PWD/implementacion/.tools/bin:$PATH"
make -C implementacion test
make -C implementacion demo
```

The local replacement now exercises F09 and F10 before results authorization,
then again at directed admission after valid results issuance. F09 deletes only
the provenance referrer. F10 signs a labelled laboratory fixture with the current
run's trusted local key, without uploading it during preparation. The fixture
changes only `buildDefinition.externalParameters.workflow.repository`; its digest,
revision, build type, builder and remaining predicate fields are unchanged.
Signing is preparation, never part of negative consumption. This is a simulated
trusted-producer fault, not a claim that an untrusted actor can use the run key.

Both trials require normal acceptance first, complete stable inventories and
valid unrelated evidence. F10 authenticates the exact prepared and received
fixture before interpreting its fields. CI returns `MISSING_PROVENANCE` or
`PROVENANCE_REPOSITORY_UNAUTHORIZED` (exit 42) only for the isolated conditions.
Malformed input, incorrect subject, trust, transport, duplicate evidence and
other contract failures remain integration errors (exit 1).

Directed admission uses the restricted actor, disabled image-verification cache,
unchanged trust/configuration/policy specifications and a successful initial server
dry-run. Only `tfm-provenance/require-provenance` (or its autogenerated Deployment
rule) may reject. F10 must identify `PROVENANCE_REPOSITORY`; a generic signature
threshold failure does not count. The exact diagnostic is pinned to Kyverno
1.19.1. An unknown message stops the trial for investigation.

The EXIT/INT/TERM recovery path restores the original OCI bytes and descriptor set
and performs fresh CI verification. Authorized trials additionally apply the
legitimate workload, observe rollout and verify health/version/quote responses.
Each trial retains these responses separately. Recovery runs even after unexpected
acceptance; a recovery failure prevents completion and retains both exit statuses.
SIGKILL and host loss require manual recovery from the retained backup. Registry
snapshots assume a single controlled publisher, not an atomic transaction.

## L05: actual source revisions

L05 is opt-in. Supply **both full commit IDs**, in ancestor order, reachable from
the local `main` captured during selection. Their `services/quotes-node/src` trees
must differ. A branch name, abbreviation, unreachable commit, same commit or
metadata-only change is rejected. The explicit pair is trusted run configuration;
provenance never selects its own authorized revision.

This pair exists in the current history and changes `server.js` and its tests:

```bash
GP_L05_FROM_COMMIT=7243334fe4ee7073801a86b25c90986b7d3c5ece \
GP_L05_TO_COMMIT=fc58e220e2d3f38d13216b23e61ffc31271f112f \
make -C implementacion demo
```

`l05-source.mjs` exports actual Git blobs into owned temporary storage without
checking out a branch or changing the index. It records commits, trees and file
hashes and Git file modes. Before each build, input capture checks exported bytes
and permissions against that record; edits or chmod after selection fail. Both builds still use the currently pinned
Node base passed explicitly as a build argument. This is a source-revision
experiment, not reconstruction of every historical build tool or base image.

After the existing L01/L03/L04 replacement and fault trials, L05 performs two
separate deliveries in `L05-from/` and `L05-to/`. Each reruns control tests and the
exported revision's service tests, builds the exported Docker context, scans it,
creates and verifies fresh image-specific evidence, issues results and installs
policy for exactly that revision before admission. Each must roll out a distinct
digest and pass the HTTP contract. Policy changes occur between legitimate
executions, never within F09/F10 fault/recovery trials. No broad revision allow-list
is introduced. With no pair supplied, the result is explicitly `NOT_EXECUTED`.

The first L05 rollout uses the successful L04 replacement as its predecessor;
missing or unsuccessful L04 evidence stops L05 before building. The second uses
the first L05 delivery. The parent's initial image is not the active predecessor.

Initial installation applies the policies without restarting the controller.
A later exact-revision update (L05) restarts it to refresh its policy cache:
pinned Kyverno 1.19.1 does not populate `Ready.observedGeneration`. Its
[startup sequence](https://github.com/kyverno/kyverno/blob/v1.19.1/cmd/kyverno/main.go)
synchronizes informers and [warms the policy cache](https://github.com/kyverno/kyverno/blob/v1.19.1/pkg/controllers/policycache/controller.go)
before serving admission. Restarts remain outside every fault/recovery trial.

Both paths wait for rollout and for current, non-terminating Ready Pods owned by
the current Deployment revision. The `kyverno-svc` EndpointSlices must route to
those Pods at the pinned webhook port. Up to 30 observations, separated by two
seconds, allow endpoint convergence; API errors or malformed snapshots abort.
This bounds polling attempts, not total wall time including API requests.
Logs are read by the selected Pod names, never by Deployment auto-selection.
Applied policy UIDs/generations/specs must remain unchanged and Ready.

Finally a restricted-actor **server dry-run** of the protected manifest must
respond: initial installation requires the exact singleton missing-results denial;
an L05 revision update requires acceptance of its already authorized delivery.
The initial dry-run is an availability preflight, not an additional F13 result.
The original F13 inventory checks and actual request still run unchanged. There
are no retries of webhook errors, and timeouts never count as policy detection.
The gate does not weaken identity, evidence or policy requirements.

Each readiness observation and dry-run response is retained. Cleanup also records
current Pods, EndpointSlices and explicit per-Pod logs after a failure, even when
readiness never completed. See the [readiness correction record](../../../../registros/kyverno_readiness_fix_EN.md)
for the two failed hosted attempts and actual validation limits.

## Hosted boundary

The normal hosted gate and admission use the same repository, revision, build type
and builder requirements. The hosted builder must equal the configured workflow
identity; native GitHub provenance obtains it from `job_workflow_ref` in the
[Actions producer](https://github.com/actions/toolkit/blob/main/packages/attest/src/provenance.ts).
Existing certificate, OIDC issuer, source ref/digest, runner and transparency checks
remain required. Local keys never establish hosted OIDC coverage.

Hosted F09/F10 remain **NOT_EXECUTED**. This change adds no remote mutation or
dispatch procedure. To demonstrate hosted L05, separately authorize and run the
manual workflow at two reviewed actual Actions revisions with distinct application
sources. Preserve each run ID, full `GITHUB_SHA`, image digest, native provenance,
source tests, policies, results and admission/HTTP evidence. Compare the two
complete packages and record the legitimate revision authorization for each run.
Both must pass independently. A second checkout inside one run cannot claim a new
native authenticated source revision, and the two same-commit L01/L03 images cannot
establish L05. No hosted run is dispatched by the local command above.

## Environment preflight before retrying

The [main `80c12bc` preflight](../../../../registros/f09_f10_l05_integration_validation_EN.md)
failed environment pins and reproduced Docker Hub DNS failure from BuildKit on
kind. F09/F10/L05 remain NOT_EXECUTED. Select **Golden Path - implementation**
when creating/rebuilding the devcontainer or Codespace; see the
[environment guide](../../environment.md). Preserve existing evidence first.
After the environment owner resolves the prerequisites, run the following.
Stop at a failed check; do not repeat the full demo or automatically apply the
historical firewall workaround. The bounded probe uses the same BuildKit image
and network as local delivery; smoke-env alone does not establish that path.

```bash
# Run from the repository root in the selected devcontainer.
(
  set -euo pipefail
  export PATH="$PWD/implementacion/.tools/bin:$PATH"
  make -C implementacion doctor
  make -C implementacion smoke-env
  source implementacion/versions.env
  probe_dir=$(mktemp -d)
  probe_builder="gp-connectivity-$(date -u +%s)-$$"
  trap 'docker buildx rm "$probe_builder"; rm -rf -- "$probe_dir"' EXIT
  docker network inspect kind >/dev/null
  docker buildx create --name "$probe_builder" --driver docker-container \
    --driver-opt network=kind \
    --driver-opt "image=$(jq -r '.images.buildkit.reference' implementacion/tools.lock.json)"
  printf 'FROM %s\n' "$SERVICE_NODE_IMAGE" > "$probe_dir/Dockerfile"
  timeout --signal=TERM --kill-after=10s 60s docker buildx build \
    --builder "$probe_builder" --platform linux/amd64 --pull \
    --progress=plain --provenance=false "$probe_dir"
  GP_L05_FROM_COMMIT=7243334fe4ee7073801a86b25c90986b7d3c5ece \
  GP_L05_TO_COMMIT=fc58e220e2d3f38d13216b23e61ffc31271f112f \
  make -C implementacion demo
)
```
